# CLAUDE.md — Hindsight Project Operating Instructions

## Identity & Authorship

You are a coding assistant helping Santhosh build Hindsight. All code, commits,
documentation, and pull requests belong to Santhosh. You are a tool, not an author.

**Never:**
- Put "Generated by Claude", "Co-authored-by: Claude", "AI-assisted", "claude-code",
  or any similar attribution in any commit message, PR description, code comment,
  docstring, or file header.
- Use `git commit --author` or add `Co-authored-by:` trailers.
- Add yourself to any contributor list, CONTRIBUTORS file, or package.json authors.
- Include AI watermarks, model names, or assistant signatures anywhere.

**Always:**
- Commit as the configured git user only.
- Write commit messages in the first person as the developer, not as an AI.
- Write code comments and docs as if Santhosh wrote them.
- Before every commit, check `git config user.name` — it must not contain AI names.

## Repository Structure

This is a monorepo. The structure is:
- `backend/` — FastAPI application (Python 3.11+)
- `frontend/` — React JS web application (TypeScript, Vite, Tailwind)
- `e2e/` — Playwright end-to-end tests
- `docs/` — Architecture, decisions (ADRs), module docs, interview prep
- `.claude/` — Skills, hooks, sub-agents (never commit cache/tmp/sessions)

Frontend is React JS for web. If a mobile app is added later it is React Native in
`mobile/`. Do not conflate the two.

## Module Workflow — Follow This Exactly, Every Time

Every phase in Master-Prompt.md follows this sequence. **No step may be skipped.**
**No step may run out of order.**

```
Step 1   BRANCH     create feature branch from main
Step 2   READ       re-read the phase in plan.md and Master-Prompt.md
Step 3   EXPLORE    read existing code the module touches
Step 4   DOCUMENT   write PRD + FRD + NFR → commit docs → then continue
Step 5   CODE-BE    implement backend (FastAPI) against the documents
Step 6   TEST-BE    ruff + mypy + pytest → 100% pass → fix failures → repeat
Step 7   REVIEW-BE  spawn code-reviewer sub-agent → fix all BLOCKING → re-review
Step 8   CODE-FE    implement frontend (React JS) against the same documents
Step 9   TEST-FE    tsc + build + vitest → 100% pass → fix failures → repeat
Step 10  REVIEW-FE  spawn code-reviewer sub-agent → fix all BLOCKING → re-review
Step 11  TEST-E2E   spawn e2e-tester sub-agent → 100% pass → fix failures → repeat
Step 12  PUSH       push branch → pre-push hook runs automatically
Step 13  PR         create pull request with filled template
Step 14  MERGE      merge after all CI checks green → delete branch
```

**Step 4 detail:** docs are committed before any code is written.
Commit message: `docs(phase-N): add PRD, FRD, NFR for <module name>`
Then and only then start Step 5.

**Step 6 / Step 9 / Step 11 detail:** 100% pass means:
- Zero ruff errors
- Zero mypy errors
- Zero pytest failures
- Zero tsc errors
- Build succeeds
- Zero e2e failures
If any check fails, fix the code (not the test) and re-run from the top of that step.

## Architecture Rules

- One database: PostgreSQL 16 + pgvector. No Neo4j, no Chroma, no Redis.
- Backend: FastAPI async, SQLAlchemy 2.0 async, Alembic, Pydantic v2.
- Frontend: React 18, TypeScript strict, Vite, Tailwind, shadcn/ui, React Query.
- Mobile (future only): React Native with Expo managed workflow.
- Every tenant query filters workspace_id — enforced in the repository layer.
- Async throughout. Never block the event loop in a request handler.
- Pydantic v2 models at every module boundary. No bare dicts.
- LLM calls only in background workers or agent nodes. Never in request handlers.
- Full type hints on every function. mypy strict must pass.

## After Each Phase

Write before moving to the next phase:
1. `docs/decisions/NNNN-<slug>.md` — one ADR per non-obvious decision. Two paragraphs.
2. Append to `docs/interview-prep.md` — Q&A for that phase's design choices.

## What Never to Do

- Never push directly to main.
- Never edit a committed Alembic migration.
- Never commit .env.
- Never hardcode an API key, model ID, or secret string.
- Never call the LLM in a request handler.
- Never skip tests because they are failing. Fix the code.
- Never skip the e2e step. If e2e tests don't exist for the module yet, write them.
